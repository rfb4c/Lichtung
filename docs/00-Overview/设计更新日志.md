## 待实施设计决策（已讨论，尚未开发）

### 右侧栏重设计（讨论日期：2026-03-10）

**背景**：原右侧栏完全模仿 Twitter（热门话题、关注推荐），所有元素均无实际功能，与研究目标无关。

**决策结果**：

| 元素 | 决策 | 说明 |
|---|---|---|
| 搜索框 | ✅ 保留并实现 | 按 Topic 名称搜索，回车确认，筛选主 Feed |
| 热门话题卡片 | ❌ 移除 | 与研究目标相悖，不应强化已有热点 |
| 关注推荐 / Follow 按钮 | ❌ 移除 | 与平台定位无关 |
| Show more | ❌ 移除 | 无内容支撑 |
| **冷门话题入口** | 🔜 占位保留，未来实现 | 见下方 |

**搜索交互规范**：
- 搜索对象：`topic.name`（议题名称，如 "Gun Control"）
- 触发方式：按 Enter 确认
- 效果：主 Feed 只显示该 Topic 下的报道
- 重置方式：点击侧边栏 Home 按钮回到全部 Feed（无需额外"清除"按钮）

**冷门话题（未来功能）**：
- 设计动机：主动引导用户接触关注度较低的议题，增加信息多样性，符合降低感知极化的研究目标
- 定义待定：候选方案为"评论数/报道数最少的 Topic"，或手动标记
- 交互方式：点击后与搜索筛选效果相同（筛选 Feed）
- **当前阶段**：仅保留 UI 入口（占位卡片），不实现筛选逻辑

### 未来功能规划（讨论日期：2026-03-10）

以下功能已形成方向共识，暂不实现，仅作规划记录：

- 重定位：不关注人，而是关注议题（Topic）
- 研究价值：用户主动订阅议题的选择行为，可作为干预效果的测量指标

- 与评论回复功能联动（前置依赖：嵌套评论）

**评论回复功能（嵌套评论）**
- 目前只有顶层评论，未来实现嵌套回复，是 Notifications 的前置依赖

**信息饮食透明度（Information Diet）**
- 研究价值：**高**，直属感知极化干预范畴，有文献支持（元认知干预）
- 展示用户本次访问浏览了哪些 Topic 的报道，如"你今天浏览了 Gun Control (5篇)、Climate Policy (2篇)"
- 位置候选：右侧栏下方 / Profile 页
- 实现前置条件：需要浏览行为记录（前端 sessionStorage 或 Supabase 行为日志）

**Explore → 议题探索页**
- 研究价值：**中-高**，鼓励用户主动接触不熟悉的议题
- 展示所有 Topic 的卡片列表，每张卡片显示议题名、报道数、简介
- 点击进入该 Topic 的筛选 Feed

**先评论后看评论（Comment-First）**
- 研究价值：**高**，成本**低**
- 用户展开评论区时，先显示输入框；点击"查看评论"后才加载其他人的评论
- 减少从众效应，帮助用户形成独立判断，直接对抗评论区回音壁造成的感知极化

**Discover New Topics（冷门话题）**
- 右侧栏占位已实现，筛选逻辑待实现

## v0.4.4 — 死字段与数据流整顿 (2026-08-15)

### 零配置可运行

`src/lib/supabase.ts` 原先在模块顶层无条件执行 `createClient`。`supabase-js` 在 url 为 `undefined` 时同步抛异常，而该模块被 `App.tsx` / `AuthContext.tsx` 顶层 import——异常发生在任何组件渲染之前，整棵 React 树挂载不上，各处 `isSupabaseConfigured` 的降级分支永远没机会执行。表现为：零配置克隆仓库后打开就是白屏，且界面上没有任何提示。

改为未配置时返回一个"访问即报错"的哨兵对象。哨兵只在某个调用点漏掉 `isSupabaseConfigured` 判断时才会被碰到，报错信息直接指出漏判的属性名。同时 `config.ts` 增加 anon key 校验（此前只校验 url），技术设计文档里给出的占位 `.env` 现在也正确判为未配置。`ProfilePage` 的头像上传补上判断——它是整个仓库唯一没有保护的 Supabase 调用点。

副作用：零配置构建下 Rollup 可以整体摇掉 Supabase SDK，产物从 435 KB 降到 256 KB。

### Path B 挂载统一到单一解析路径

此前 `FeedItem` 与 `CommentSection` 各有一套民调解析逻辑：前者按 `report.pollingDataId`，后者按 `topicId` 做议题级兜底。同一篇报道，"Public Opinion" 按钮的显隐与评论区顶部图表的显隐可能不一致；4 篇明确写了 `pollingDataId: null` 的报道照样弹出图表。

新增 `src/lib/pollingResolver.ts` 作为唯一入口，挂载与否只看 `report.pollingDataId`，不做议题级隐式兜底，由 `FeedItem` 解析后传给 `CommentSection`。同时删去 `FeedItem` 里针对 `us-gun-control` 的硬编码特例。

**`null` 是有意义的状态，不是数据缺口**：Path B 的前提是"真实分布比公众以为的更有共识"。若某个具体调查问题的权威数据本身就呈两极分布，挂出来只会印证极化感知而非校正它，此时不干预才是正确行为。据此，民调库的入库判据与"挂/不挂"的判定需要单独定案并留档（见当前快照 § 下一步）。

`mappers.ts` 的 `mapPollingData` / `PollingDataRow` 一并移除：`app-data.json` 是民调的唯一事实源，Supabase 里的 `polling_data` 由同步脚本从该文件生成，前端不再反向读库。

### 死字段清除

`app-data.json` 的 28 篇报道移除 `hostilityScore` 与 `contentType`。两者在 `src/` 内零引用，`Report` 类型中也未声明——Path A 的排序早已不使用敌意维度（详见 Path A 设计规范开头的实装状态说明）。线上表的对应列因 `DROP COLUMN` 不可逆，留在同步脚本里作为注释掉的手动步骤，不随同步自动执行。

### 评论数改真实计数

`FeedItem` 的评论数原先是 `report.id` 哈希出的伪随机数（最大可到 90 多），而静态数据里本就有 76 条 mockComments 可以真实统计。改为以静态计数为基线（新增 `src/lib/commentCounts.ts`），Supabase 模式下用数据库计数覆盖在基线之上。

用合并而非替换是必要的：数据库里没有评论的报道，`CommentSection` 会回落到 mockComments 渲染，若计数不跟着回落，用户发出一条评论后徽标会从 3 掉到 1。

### 测试

Playwright 无头浏览器 19 项断言 × 3 种配置（真实 Supabase / 无 `.env` / 占位 `.env`）全部通过，三种模式渲染结果完全一致：28 篇报道、14 篇挂载分布图、评论总数 76、抽样报道的徽标数与实际渲染条数相等。`npm run build` 通过；eslint 问题数与改动前基线相同。
