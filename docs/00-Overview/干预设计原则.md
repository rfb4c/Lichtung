# 干预设计原则

> 本文件记录 Lichtung 系统在设计和部署干预功能时需遵守的底层原则。
> 适用于所有干预路径（Path A/B/C 及未来扩展）。

---

## 原则一：问题粒度原则

**同一议题下，不同粒度的问题会产生完全不同的分布。**

选择 polling 问题时，应根据"这道题能讲出什么故事"来决定，而不是按议题机械对应。

**含义**：
- 例如，"是否支持背景调查"与"是否支持禁售突击步枪"同属枪支管制议题，但前者 88% 支持，后者约 56% 支持——适合讲的故事完全不同
- 权衡型问题（"你认为枪支权利与安全哪个更重要？"）比是非型问题更容易呈现中间立场
- 跨党派共识型数据（两党各有多大比例支持某措施）是另一类有效的叙事角度

**决策顺序**：先确定要讲的故事 → 再找支持该故事的数据 → 而不是先有数据再硬套叙事。

---

## 原则二：干预匹配原则

**不同报道不应强行套用同一种干预。根据该报道的数据条件，选择最能有效校准感知偏差的干预手段。**

**含义**：
- 如果一篇报道对应的 polling 数据确实支持"温和多数"叙事 → 使用 Path B（温和多数可视化）
- 如果数据不支持温和多数，但报道涉及具体人物或群体 → 优先使用 Path C（交叉身份）
- 同一篇报道可以同时部署 Path B 和 Path C，两者不互斥
- 某些报道可能暂时不适合任何干预，强行配置反而损害叙事可信度

**实际操作**：每篇报道（或每个 subtopic）应单独决定部署哪种干预，而非由所属 topic 统一决定。

---

## 待补充原则

以下方向在实践中可能发展为新原则，暂做记录：

- 叙事一致性原则：同一 demo 流程中，呈现给用户的干预逻辑应前后一致，不应在不同报道间切换矛盾的叙事框架
- 显著性控制原则：干预线索不应过于突兀，避免用户意识到研究目的（demand effect）
